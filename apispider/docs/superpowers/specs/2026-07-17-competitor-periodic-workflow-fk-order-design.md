# 竞品周期任务工作流外键顺序修复设计

## 背景

竞品周期扫描器领取到期目标时，会在同一事务中创建 `WorkflowRecord`，并把新工作流 ID 写入竞品账号或视频的 `active_workflow_id`。PostgreSQL 在工作流记录尚未插入时执行目标更新，触发外键约束错误，导致周期扫描失败。

## 根因

`CompetitorRepository.claim_due_targets` 先修改已经处于持久化状态的目标，再把新工作流加入 SQLAlchemy Session。模型没有通过 ORM relationship 表达目标与活动工作流之间的依赖，因此不能依赖 Unit of Work 自动保证工作流插入先于目标更新。

新增监控目标的 `add_target` 已采用显式顺序：添加工作流、`flush`、再添加引用工作流的目标。周期领取逻辑没有复用这一顺序。

## 方案

在每个到期目标的领取事务中：

1. 创建工作流并加入 Session。
2. 立即执行 `session.flush()`，保证工作流行已在当前事务中存在。
3. 再设置目标的 `active_workflow_id` 和刷新状态。
4. 保留最终统一 `commit`，确保领取锁、工作流创建和目标更新仍然原子提交。

不修改数据库结构、调度接口或工作流生命周期。

## 测试

周期扫描测试使用 SQLite，并显式开启 `PRAGMA foreign_keys=ON`。测试保存一个到期竞品账号和一个到期竞品视频，执行一次扫描后断言两个工作流均已持久化、目标外键均指向对应工作流。修复前测试应因外键约束失败，修复后通过。

## 约束

- 后端命令只使用名为 `starx` 的 conda 环境。
- 不修改用户现有的未跟踪文件。
- 修复范围只覆盖周期领取事务及其回归测试。
