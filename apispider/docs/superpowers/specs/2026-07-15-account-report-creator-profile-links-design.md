# 账号报告博主主页链接设计

## 1. 背景

账号报告的“相似账号”和“头部博主参考”目前只保存 AI 返回的脱敏名称、创作者哈希和分析信息。MediaSpider 在采集边界已经移除真实昵称与主页链接，因此数据库和前端无法恢复公开账号的真实名称，也无法从报告直接跳转到博主主页。

本次改动需要同时满足两类边界：

1. AI 只接收脱敏、最小化的分析证据，不接收真实昵称或主页链接。
2. 数据库与前端保存、展示采集到的公开真实昵称和主页链接。

此外，小红书笔记的公开链接必须保存搜索结果对应的完整地址，包括 `xsec_token` 与 `xsec_source` 查询参数。该笔记链接允许进入 AI prompt；它与禁止进入 AI 的博主主页链接属于不同数据边界。

## 2. 目标

- MediaSpider 的内部采集结果保留公开创作者的真实昵称和规范主页链接。
- 账号报告 AI prompt 继续使用脱敏昵称，且不包含任何主页链接。
- AI 只能选择采集证据中的候选账号，不能提供或修改主页链接。
- 工作流在 AI 分析完成后，按平台和创作者哈希合并可信的真实昵称与主页链接。
- `similarAccounts` 和 `topBloggerDetails` 将 `profileUrl` 一并保存到现有 JSON 字段，不新增数据库列。
- 前端账号名称可点击，并在新窗口打开对应平台主页。
- 历史报告保持兼容；没有 `profileUrl` 时按普通文本展示，重新生成后获得链接。
- 小红书采集结果的现有 `note_url` 字段保存完整公开笔记链接，不拆分或新增 token 字段。
- 行业合规提醒同时覆盖已采集内容中的风险与未来创作容易出现的行业风险，不能只复盘现有笔记。

## 3. 非目标

- 不回填无法从现有报告恢复的历史主页链接。
- 不允许 AI 返回的名称或 URL 覆盖采集证据。
- 不调整账号报告的候选数量、排序、合规、用户画像或选题下游逻辑。
- 不新增独立博主表，也不修改现有数据库表结构。
- 不把推演风险描述成当前账号或样本已经违规，也不编造法规条款、处罚结果或平台公告。

## 4. 方案选择

采用“展示证据与 AI 证据分离”的双通道方案。

### 4.1 未采用方案

直接把真实资料交给 AI 再要求原样返回，虽然改动较少，但会扩大敏感信息边界，且无法保证 AI 不遗漏或改写链接。

只保存创作者 ID 并由前端拼接主页 URL，会把平台规则泄漏到前端；平台 URL 结构变化时也更难统一维护。

## 5. 架构与数据流

```text
平台公开数据
  -> MediaSpider 内部结果（真实昵称、profileUrl、creatorHash）
  -> 账号报告展示证据（保留真实资料，仅供工作流内部合并）
  -> AI 证据投影（昵称脱敏、移除 profileUrl）
  -> AI 分析结果（相似原因、内容特征、指标等）
  -> 候选白名单过滤
  -> 按 platform + creatorHash 合并真实 name/profileUrl
  -> reports.similar_accounts / reports.top_blogger_details
  -> 报告 API
  -> 前端安全链接
```

职责边界如下：

- MediaSpider store 负责从平台原始数据提取稳定 ID、公开昵称和规范主页 URL。
- 小红书 store 负责把详情记录中的 `note_id`、`xsec_token`、`xsec_source` 编码成完整 `note_url`；证据层继续映射为报告的 `publicUrl`。
- 账号报告证据层负责排序、去重、当前账号排除，以及构造 AI 专用脱敏投影。
- 账号报告 workflow 负责验证 AI 候选并从可信证据合并展示字段。
- 数据库服务继续按 JSON 原样持久化和返回结构化报告。
- 前端只渲染通过安全 URL 校验的链接。

## 6. 数据契约

### 6.1 内部创作者证据

`CreatorEvidence` 增加：

- `display_name` / `displayName`：平台返回的公开真实昵称，仅用于持久化展示。
- `profile_url` / `profileUrl`：后端生成或平台返回的规范公开主页链接，仅用于持久化展示。
- 现有 `name` 继续作为 AI 使用的脱敏昵称。

如果实现中使用独立的展示模型，只要满足同样的边界也可以；不得通过把真实字段直接序列化进 AI prompt 来简化实现。

### 6.2 持久化报告

`similarAccounts[]` 与 `topBloggerDetails[]` 各增加可选字段：

```json
{
  "name": "公开真实昵称",
  "profileUrl": "https://平台规范域名/主页路径"
}
```

现有 JSON 列可以直接保存新字段，因此不需要 Alembic 迁移。老数据缺少字段时保持可读取。

### 6.3 AI 输出契约

AI 输出契约不增加 `profileUrl` 或真实昵称字段。AI 返回的 `name` 不作为最终展示名称的权威来源；候选通过白名单后，由工作流用采集证据覆盖。

## 7. 主页链接构造与安全

主页链接必须从稳定的原始创作者 ID 构造，并限制在支持平台的 HTTPS 正式域名：

- 小红书：`https://www.xiaohongshu.com/user/profile/{user_id}`
- 抖音：`https://www.douyin.com/user/{sec_user_id}`
- 快手：`https://www.kuaishou.com/profile/{user_id}`

链接构造发生在原始 ID 哈希前。输出只允许 `https` 且主机名命中平台白名单，不接受原始数据中的任意外部 URL。无法获得稳定 ID 时使用空字符串，不能猜测。

前端再执行一次展示侧校验，仅允许 `http/https`；协议异常、解析失败或空链接时降级为普通文本。链接使用 `target="_blank"` 与 `rel="noopener noreferrer"`。

## 8. AI 脱敏边界

构造 prompt 时必须通过显式投影生成 AI 证据，不能直接序列化包含展示字段的内部模型。投影继续包含分析所需的：

- 平台；
- 创作者哈希；
- 脱敏昵称；
- 粉丝、作品和互动指标；
- 命中内容数和代表内容。

投影必须排除 `displayName`、`profileUrl`、原始用户 ID 和其他既有敏感字段。现有评论与账号上下文脱敏规则保持不变。

公开笔记链接不属于本节的博主主页限制。`ContentEvidence.publicUrl` 可以携带完整小红书 `note_url` 进入 AI prompt，其中允许包含该笔记搜索结果返回的 `xsec_token` 与 `xsec_source`。AI 仍不得编造链接。

## 8.1 小红书完整笔记链接

小红书 `update_xhs_note` 使用详情记录中的现有字段构造：

```text
https://www.xiaohongshu.com/explore/{note_id}?xsec_token={xsec_token}&xsec_source={xsec_source}
```

查询参数必须通过标准 URL 编码生成，不能用字符串拼接破坏 token 中的 `=`、`+` 等字符。两个查询参数均存在时保存完整链接；缺少任一参数时兼容保存不带查询参数的基础笔记链接。完整地址只保存在现有 `note_url` 字段，后续证据模型沿用 `publicUrl` 映射，不新增数据库字段。

## 9. 前端交互

- 相似账号概览：名称有链接时可点击进入主页。
- 相似账号完整名单：账号标题有链接时可点击进入主页。
- 头部博主参考：博主名称有链接时可点击进入主页。
- 链接应复用统一的小型组件或纯函数，避免三个位置分别实现安全判断。
- 可点击状态使用现有报告视觉语言，不改变卡片布局；键盘焦点应清晰可见。

## 9.1 行业合规提醒生成原则

`complianceRules` 沿用现有 `riskLevel`、`expression`、`reason`、`suggestion`、`platforms` 契约，不增加数据库字段。AI 必须生成两类互补提醒：

1. **证据复盘风险**：从当前账号和行业公开笔记中识别已经出现的高风险或易误导表达。
2. **行业预防风险**：即使样本暂未出现，也要结合 `accountContext` 中的行业、产品/服务、目标受众、转化目标和目标平台，推演后续创作中容易踩坑的具体方向。

行业预防风险必须与当前业务相关，不能输出任何行业都适用的空泛提示。`expression` 给出创作时应避免的代表性表达，`reason` 明确这是预防性行业风险及其风险逻辑，`suggestion` 给出可直接采用的稳健替代表达。没有证据证明已发生时，不得使用“当前账号已违规”“样本已违法”等确定性结论，也不得虚构法规编号、处罚结果或平台公告。

## 10. 错误处理与兼容

- AI 返回不存在的候选：继续由既有白名单过滤移除。
- AI 试图返回或篡改 URL：输出模型不接收该字段，最终 URL 只来自采集证据。
- 平台没有稳定 ID：保存空 `profileUrl`，前端展示不可点击名称。
- 历史报告没有新字段：API 和前端正常读取，不报错。
- 同一创作者同时出现在相似账号和头部博主中：两个结果都从同一可信证据映射合并，保持一致名称和链接。

## 11. 测试策略

### 11.1 后端

1. MediaSpider store 测试：三个平台均能从原始稳定 ID 生成正确主页链接并保留公开昵称。
2. 证据测试：内部展示证据含真实字段，AI 投影仍为脱敏名称且不含主页链接。
3. workflow 测试：AI 选择合法候选后，持久化结果由证据补入真实名称和 `profileUrl`。
4. 安全测试：AI prompt 不包含真实昵称、主页链接或原始用户 ID；AI 伪造字段不能进入持久化结果。
5. 兼容测试：无主页链接的候选仍可生成并持久化报告。
6. API/数据库测试：新增 JSON 字段原样往返。
7. 小红书 store 测试：包含 `=` 等字符的 `xsec_token` 被正确编码并保存在完整 `note_url`，缺少参数时仍保存基础链接。
8. prompt 测试：明确要求同时生成证据复盘和行业预防风险，允许样本未出现时基于账号行业与目标平台推演，但禁止冒充已发生事实或编造法规条款。

### 11.2 前端

1. 安全 URL 纯函数接受合法 HTTP(S)，拒绝脚本协议和无法解析的值。
2. 三个展示位置都使用 `profileUrl` 生成新窗口链接。
3. 缺少或不安全链接时渲染普通文本。
4. 运行账号报告相关预览测试与前端完整测试。

## 12. 验收标准

新生成的账号报告中，相似账号和头部博主展示公开真实昵称；存在稳定主页 ID 时，点击名称可以直接打开正确平台的账号主页。数据库 JSON 保存真实昵称和 `profileUrl`，API 原样返回。发送给 AI 的 prompt 中不出现真实昵称、博主主页链接或原始用户 ID，且 AI 无法注入或篡改最终博主主页链接。小红书笔记的现有 `note_url` 保存包含 `xsec_token`、`xsec_source` 的完整公开地址，该地址允许映射为 `publicUrl` 进入 AI prompt 和账号报告。行业合规提醒既复盘已有内容，也覆盖未来创作容易出现的行业风险，且不会把预防性推演伪装成已发生违规。历史报告无需迁移并保持正常展示。
