# 账号报告多 Cookie 并行关键词采集设计

## 1. 背景与问题

账号报告当前为每个平台生成 3～5 个关键词，并把整组关键词交给一次 MediaSpider 运行。平台爬虫内部按关键词串行处理，因此即使 `cookies.json` 为同一平台配置了多个 Cookie，也只会选择其中一个 Cookie 完成整组关键词。

现有实现还有两个重要约束：

1. `run_with_cookie_candidates` 只在当前 Cookie 被分类为凭证失效时轮换下一个候选，不管理 Cookie 的占用、冷却或跨 workflow 互斥。
2. MediaSpider 运行时会临时写入模块级全局配置，因此 `run_crawler` 使用进程级全局锁串行保护所有爬虫。直接删除该锁会导致并行任务之间的 Cookie、关键词和运行参数互相覆盖。

结果是多个有效 Cookie 无法转化为关键词级吞吐量，账号报告总耗时接近各关键词耗时之和。与此同时，多个账号报告并发启动时也缺少“同一个 Cookie 不能同时使用”的全局资源边界。

## 2. 目标

1. 将账号报告的每个关键词拆成独立采集单元，并使用不同 Cookie 并行执行。
2. 同一后端进程内按平台全局租赁 Cookie，任何两个账号报告不得同时使用同一个 Cookie。
3. 每个平台最多并行运行 3 个采集单元；实际并发数取空闲 Cookie、待执行单元和平台并发上限的最小值。
4. 凭证失效的 Cookie 立即禁用，直到 `cookies.json` 内容更新。
5. 风控、限流、请求超时等临时异常采用指数退避冷却，并允许采集单元切换到尚未尝试的 Cookie。
6. 所有 Cookie 正在使用或冷却时，采集单元公平等待，不重复占用、不忙轮询、不无限重试。
7. 使用独立子进程隔离每个采集单元的 MediaSpider 模块级配置与浏览器生命周期。
8. 多关键词结果安全去重合并，单个关键词失败不丢弃其他成功结果。
9. 进度展示明确区分单元计数与平台累计，不再把整批累计评论误显示在某条内容旁。
10. Cookie 不进入命令行、日志、异常、进度、持久化结果或对象字符串表示。
11. 爬虫中途失败时保留已取得的完整安全结果，继续切换 Cookie 或退避重试；最终仍失败但已有可用结果时，基于部分结果生成报告。

## 3. 非目标

- 第一版不实现跨后端进程或跨机器的分布式 Cookie 租约。多 Worker 部署需要后续迁移到 Redis 等共享协调设施。
- 不在本次重构中把三个平台的全部模块级配置改造成实例配置。
- 不修改关键词规划数量、每关键词内容上限、单内容评论上限或最终报告证据容量。
- 不保证采集速度随 Cookie 数量线性增长；平台响应、浏览器启动、请求间隔和机器资源仍会影响耗时。
- 不把内容不存在、参数错误等确定性错误伪装成 Cookie 故障。
- 不在子进程中直接访问 workflow 数据库或修改账号报告状态。
- 不把只有评论、但没有任何对应内容或账号的孤立结果视为可用报告证据。

## 4. 方案概览

采用“工作流层拆分关键词 + 主进程全局 Cookie 租约 + 独立子进程采集 + 主进程结果合并”方案。

```text
账号报告 workflow
  ├─ 当前账号主页采集单元
  └─ 3～5 个关键词采集单元
                │
                ▼
      平台级全局调度器（主进程）
      ├─ Cookie 租约状态机
      ├─ FIFO 等待队列
      ├─ 平台并发上限 = 3
      └─ 重试轮次与总时限
                │
       每个租约对应一个独立子进程
                │
                ▼
      MediaSpider + 独立浏览器上下文
                │
                ▼
       结构化进度 / 结果 / 失败代码
                │
                ▼
      主进程去重合并并继续报告分析
```

账号主页采集也必须经过同一个租约管理器。否则主页任务与关键词任务可能绕过互斥边界，同时使用同一个 Cookie。

## 5. 模块边界

### 5.1 `GlobalCookieLeaseManager`

新增进程级租约管理器，职责仅包括：

- 加载并校验各平台 Cookie 快照。
- 为每个 Cookie 生成仅在内部使用的稳定槽位标识和不可逆摘要。
- 维护 Cookie 的可用、租用、冷却和禁用状态。
- 按平台提供异步租约申请与释放接口。
- 维护 FIFO 等待顺序并在状态变化时唤醒等待者。
- 检测 `cookies.json` 内容变化并原子替换快照。
- 提供不含 Cookie 内容的诊断快照。

租约对象实现异步上下文管理器。正常完成、异常、取消和子进程崩溃都必须通过同一出口归还或变更 Cookie 状态。

### 5.2 `PlatformCrawlScheduler`

每个平台一个逻辑调度器，职责包括：

- 接收主页和关键词采集单元。
- 使用平台信号量把运行中子进程数限制为 3。
- 向租约管理器申请 Cookie。
- 记录当前单元已经尝试过的 Cookie 摘要和重试轮次。
- 根据标准化错误类别决定成功释放、永久禁用、指数冷却或立即失败。
- 保证取消 workflow 后不再启动其排队单元。

租约可用性和平台并发额度必须同时满足才允许启动子进程。调度器不得先占用 Cookie 再长时间等待并发额度，也不得先占用并发额度后长时间等待 Cookie。

### 5.3 `CrawlerSubprocessRunner`

子进程运行器负责：

- 使用 `spawn` 方式创建全新解释器进程，避免继承父进程内已经修改的爬虫全局状态。
- 通过私有 IPC 管道传入单个采集单元配置和 Cookie。
- 在子进程中构造 `CrawlerRunConfig`、启动 MediaSpider 和浏览器。
- 将白名单进度事件、最终 `CrawlResult` 或标准化失败代码返回主进程。
- 超时、取消或崩溃时终止完整浏览器进程树并关闭 IPC。

Cookie 不得作为命令行参数、普通环境变量、临时文件名或日志字段传递。IPC 消息对象必须排除 `repr`，异常处理不得序列化完整输入。

### 5.4 `CrawlResultMerger`

结果合并器是独立无状态组件：

- 内容按 `平台 + content_id` 去重。
- 评论按 `平台 + comment_id` 去重。
- 账号按 `平台 + creator_hash` 去重。
- 同一内容被多个关键词命中时合并关键词来源集合。
- 字段冲突时优先选择采集时间更新且非空字段更完整的记录。
- 输出稳定顺序，避免并发完成顺序造成报告输入随机漂移。

### 5.5 `PartialResultAccumulator`

每个采集单元拥有跨 Cookie 尝试存在的部分结果累加器，职责包括：

- 接收子进程成功结果或失败时返回的完整安全 `CrawlResult`。
- 在每次 Cookie 切换前保存已取得的内容、评论和账号。
- 复用 `CrawlResultMerger` 按稳定标识去重，避免重试导致重复放大计数。
- 只保留能够关联到已采集内容的评论；没有内容或账号的孤立评论不能使结果变为可用。
- 提供 `has_usable_evidence`，其定义为至少包含一条内容或一条账号记录。
- 在重试耗尽后生成 `partial` 单元结果，供 workflow 继续构建报告证据。

## 6. Cookie 状态模型

每个平台 Cookie 具有以下状态：

| 状态 | 含义 | 可否分配 |
|---|---|---|
| `available` | 可立即使用 | 是 |
| `leased` | 已租给一个运行中采集单元 | 否 |
| `cooling_down` | 临时异常后的退避期 | 否，冷却结束后自动恢复 |
| `disabled` | 凭证失效 | 否，配置内容更新前不恢复 |

状态中只保存必要元数据：平台、槽位标识、Cookie 摘要、租约 ID、连续临时失败次数、冷却截止时间和配置版本。公开诊断不得返回 Cookie 摘要。

### 6.1 成功

采集成功后：

1. 当前租约释放。
2. Cookie 转为 `available`。
3. 连续临时失败次数清零。
4. 唤醒对应平台等待队列。

### 6.2 凭证失效

只有错误分类明确为 `credentials_expired` 时才永久禁用：

1. Cookie 转为 `disabled`。
2. 当前采集单元把该 Cookie 记为已尝试。
3. 调度器尝试尚未使用且可用的 Cookie。
4. 当前配置版本内，该 Cookie 不再分配给任何 workflow。

配置文件仅修改时间但内容不变时不得恢复禁用 Cookie。

### 6.3 临时异常

风控、限流、请求超时和明确可重试的平台临时异常采用指数退避：

```text
30 秒 → 60 秒 → 120 秒 → 240 秒 → 480 秒 → 最大 600 秒
```

当前 Cookie 进入 `cooling_down`，采集单元优先尝试本轮尚未使用的其他 Cookie。成功完成一次采集后，该 Cookie 的连续临时失败次数清零。

网络配置错误、内容不存在、参数错误、结果校验错误等确定性异常不切换 Cookie，采集单元立即失败。

## 7. 等待、公平性与重试边界

### 7.1 等待规则

- 所有 Cookie 正在租用时，采集单元进入平台 FIFO 队列。
- 有 Cookie 在冷却且没有可用 Cookie 时，等待最早冷却截止时间或其他租约提前释放。
- 租约释放、冷却结束、Cookie 禁用或配置重载都会触发条件重新计算。
- 等待使用异步条件变量和可取消超时，不使用固定频率忙轮询。
- 一个失败后需要切换 Cookie 的采集单元重新进入队尾，避免长期占用调度机会。

### 7.2 重试边界

- 每个 Cookie 每轮最多尝试一次。
- 本轮所有候选 Cookie 都发生临时失败后，等待冷却并进入下一轮。
- 单个采集单元最多执行 3 轮。
- 单个采集单元包含排队、冷却和运行时间在内的总时限为 15 分钟。
- 凭证失效的 Cookie 不计入后续轮次候选。
- 超出轮次或总时限后，若部分结果累加器有可用证据，则当前单元标记为 `partial`；否则标记为 `failed`。其他关键词和平台继续。

如果平台所有 Cookie 都被禁用，等待中的采集单元立即收到公开的“平台凭证已失效”失败，不等待到总时限。

## 8. 配置文件更新与版本切换

主进程每次准备分配租约前检查 `cookies.json` 内容指纹。指纹使用规范化后的平台 Cookie 列表计算，不依赖修改时间。

内容变化时执行原子重载：

1. 完整读取、校验并规范化新文件；解析失败时保留旧快照并报告安全配置错误。
2. 生成新的配置版本。
3. 新增 Cookie 进入 `available`。
4. 已删除且未租用的 Cookie 立即移除。
5. 已删除但仍在租用的 Cookie 标记为退役，当前任务结束后移除，不强制中断。
6. 新版本中仍存在的 Cookie 清除旧版本的 `disabled` 状态，视为运维已确认更新；若希望保持禁用，应从配置中删除。
7. 冷却和失败计数按新版本重置。

重载过程不得输出文件路径之外的敏感内容，也不得在部分解析成功时替换当前有效快照。

## 9. 子进程数据流与生命周期

主进程向子进程传入：

- 采集单元 ID、workflow ID 的安全内部引用。
- 平台、采集类型、单个关键词或主页地址。
- 运行上限、请求间隔、浏览器与代理配置。
- 当前租约 Cookie。

子进程只返回：

- 白名单进度事件。
- 成功时的 `CrawlResult`。
- 失败时的完整安全部分 `CrawlResult`、公开错误代码及内部非敏感分类。

现有 `CrawlerExecutionError.partial_result` 只保留三个计数，会丢弃已经采集的内容、评论和账号。实现必须调整为保留经过内存存储安全转换后的完整 `CrawlResult`；Cookie、请求头、底层异常对象和未清洗原始响应仍不得进入异常或 IPC 消息。

主进程是 workflow 状态和数据库持久化的唯一写入者。子进程不得持有数据库 Session，不得直接调用 `WorkflowStore`。

生命周期规则：

1. 子进程启动失败视为临时运行时异常，回收租约并按重试边界处理。
2. 子进程超过 15 分钟总时限时先发送温和终止，短暂等待后强制终止进程树。
3. workflow 被取消时，排队单元移出队列，运行单元终止子进程并回收租约。
4. 主进程退出时执行统一清理；异常退出后的浏览器孤儿进程由子进程父进程死亡保护机制兜底。
5. 子进程成功结果和失败部分结果只有在完整校验通过后才进入累加器，部分损坏消息不能污染已成功结果。
6. 子进程失败后，主进程先合并本次部分结果，再根据错误分类禁用、冷却或释放 Cookie，并决定是否重试。

## 10. 账号报告 workflow 改造

当前关键词采集从“一次调用包含全部关键词”调整为：

1. 关键词规划仍生成 3～5 个不重复关键词。
2. 为每个平台、每个关键词创建独立 `KeywordCrawlUnit`。
3. 同一平台的单元提交给平台调度器，不同平台也遵守各自租约和并发上限。
4. 使用结构化并发等待所有属于当前 workflow 的单元完成。
5. 每次成功结果或失败部分结果立即交给当前单元的 `PartialResultAccumulator`。
6. 发生凭证失效或临时异常时，先保留部分结果，再按既定租约规则切换 Cookie 或退避重试；后续结果与已有部分结果去重合并。
7. 任意一次尝试完整成功时，单元状态为 `completed`。
8. 重试耗尽但累加器至少包含一条内容或一条账号时，单元状态为 `partial`，保留公开失败代码并继续参与证据构建。
9. 只有评论且没有内容或账号时丢弃孤立评论，单元状态仍为 `failed`。
10. 平台至少有一个 `completed` 或 `partial` 单元时可继续生成报告。
11. `sourceMeta.failedPlatforms` 只记录完全没有可用结果的平台；部分成功平台通过关键词级安全采集摘要说明不完整性。
12. 只有所有支持平台的主页和关键词单元都没有任何内容或账号时，整个账号报告才失败。

`sourceMeta` 新增 `partialCrawls` 数组，元素使用固定结构：

```json
{
  "platform": "小红书",
  "mode": "keyword",
  "keyword": "299元",
  "failureCode": "platform_blocked",
  "contentCount": 6,
  "creatorCount": 4,
  "commentCount": 71
}
```

该字段只记录公开平台名、采集模式、已规划关键词、标准失败代码和去重后计数，不包含 Cookie 槽位、重试次数、异常文案或底层响应。旧报告缺少该字段时按空数组兼容。

主页采集保持先于关键词阶段，以便优先建立当前账号归属证据，但它同样使用全局租约和独立子进程。主页阶段结束后，关键词单元可并行执行。

## 11. 进度事件与前端展示

进度事件增加以下安全字段：

```text
crawlUnitId
unitType: creator | keyword
keyword
cookieSlot
unitStatus: pending | running | completed | partial | failed
unitContentCount
unitCreatorCount
unitCommentCount
platformContentCount
platformCreatorCount
platformCommentCount
```

`cookieSlot` 是当前配置版本内的临时编号，例如 `xhs-2`，不得使用 Cookie 摘要或稳定跨版本标识。

前端展示规则：

- 关键词活动显示单元计数，例如“关键词「299元」完成：10 条内容、182 条评论”。
- 平台摘要显示去重后的平台累计计数。
- “发现公开内容”活动只显示内容标题和单元内容进度，不在该内容旁展示平台累计评论数。
- 评论批次活动明确标注关键词或采集单元，不紧贴最后一条内容造成归属误解。
- 等待时显示“等待可用采集凭证”。
- 切换或冷却时显示“当前采集凭证暂不可用，正在切换”或“等待凭证冷却”。
- 单元重试耗尽但存在可用部分结果时显示“已保留当前采集结果，报告将基于已有数据继续生成”。
- 不向前端返回 Cookie 内容、摘要、失败次数细节或底层异常原文。

连续评论事件仍可合并以限制快照体积，但合并键必须包含 `crawlUnitId`，计数必须保持单元级与平台级语义明确。

## 12. 配置项

新增设置：

| 配置项 | 默认值 | 说明 |
|---|---:|---|
| `MEDIASPIDER_PLATFORM_MAX_CONCURRENT` | 3 | 每个平台同时运行的采集子进程上限 |
| `MEDIASPIDER_COOKIE_BACKOFF_INITIAL_SECONDS` | 30 | Cookie 首次临时失败冷却时间 |
| `MEDIASPIDER_COOKIE_BACKOFF_MAX_SECONDS` | 600 | Cookie 最大冷却时间 |
| `MEDIASPIDER_COOKIE_MAX_RETRY_ROUNDS` | 3 | 单个采集单元最大 Cookie 尝试轮次 |
| `MEDIASPIDER_CRAWL_UNIT_TIMEOUT_SECONDS` | 900 | 单个采集单元排队、冷却和执行总时限 |

环境变量继续使用 `STARX_` 前缀。所有设置使用正数校验；平台并发上限不得超过运维定义的安全硬上限。现有单 Cookie 配置保持兼容，调度器自然退化为串行执行。

## 13. 安全与可观测性

- Cookie 类型继续禁止 `repr`、序列化和日志输出。
- IPC、异常分类、进度回调和测试失败信息执行敏感字段扫描。
- 日志只记录平台、采集单元 ID、关键词安全摘要、Cookie 槽位、状态迁移和耗时。
- 提供进程内诊断计数：各平台可用、租用、冷却、禁用 Cookie 数，以及运行和等待单元数。
- 不记录 Cookie 摘要到数据库；摘要只存在于租约管理器内存中。
- 关键词正文按现有公开安全限制处理，不在内部错误中拼接完整请求信息。
- 子进程标准输出和标准错误不得作为未经清洗的公开失败信息。

## 14. 测试策略

### 14.1 租约管理器

1. 同一 Cookie 不会同时租给两个任务。
2. 不同 Cookie 可同时租给不同任务。
3. FIFO 等待顺序稳定，取消等待者不会阻塞队列。
4. 凭证失效后 Cookie 在当前配置版本永久禁用。
5. 文件修改时间变化但内容不变时不恢复禁用 Cookie。
6. 配置内容更新后原子重载并恢复新版本候选。
7. 删除租用中 Cookie 时允许当前任务完成，释放后移除。
8. 临时异常按照假时钟验证指数退避和 10 分钟上限。
9. 成功后连续失败次数清零。
10. 所有 Cookie 禁用时等待者立即失败。

### 14.2 调度器与重试

1. 每个平台最多并行 3 个采集单元。
2. Cookie 数少于 3 时并发度自动降低。
3. 一个 Cookie 临时失败后当前单元尝试尚未使用的 Cookie。
4. 每个 Cookie 每轮最多尝试一次，失败单元回到队尾。
5. 三轮或 15 分钟后停止重试。
6. 非 Cookie 确定性错误不触发轮换。
7. workflow 取消会移除排队单元并停止运行中子进程。
8. 每次失败先保存完整安全部分结果，再进行 Cookie 切换或退避。
9. 多次尝试的部分结果跨 Cookie 去重累加。

### 14.3 子进程隔离

1. 两个子进程使用不同 Cookie、关键词和运行参数时互不污染。
2. 子进程不再依赖父进程 `crawler_run_lock` 实现跨单元串行。
3. 正常退出、抛错、超时、取消和强制终止均能关闭浏览器并回收租约。
4. 损坏 IPC 消息被拒绝，不污染结果。
5. 命令行、环境、日志、异常、结果和快照均不包含 Cookie。
6. 失败消息包含完整安全部分 `CrawlResult`，但不包含原始响应和异常对象。

### 14.4 结果与 workflow

1. 内容、评论和账号按平台稳定标识正确去重。
2. 同一内容的多个关键词来源正确合并。
3. 并发完成顺序变化不影响最终结果顺序和报告输入。
4. 单个关键词失败时保留其他成功结果并生成部分成功报告。
5. 单个关键词所有尝试失败但有内容或账号时标记为 `partial` 并参与报告生成。
6. 只有评论的部分结果不视为可用，孤立评论被丢弃。
7. 所有尝试都失败且所有平台均无内容或账号时才进入整个报告失败路径。
8. `sourceMeta.failedPlatforms` 不收录存在可用部分结果的平台。
9. 主页任务与关键词任务不会共用同一个已租 Cookie。

### 14.5 前端

1. 单元计数和平台累计计数分别展示。
2. 最后一条“发现公开内容”不会承接整批评论增量。
3. 并行关键词活动可区分，连续评论事件只在同一采集单元内合并。
4. 等待、切换、冷却、部分失败和完成状态使用固定安全文案。
5. 旧 workflow 缺少新字段时保持兼容展示。
6. 部分成功单元展示“已保留当前采集结果，报告将基于已有数据继续生成”。

后端测试必须使用 `conda run -n starx pytest ...`，不得创建其他 Python 或 Conda 环境。

## 15. 验收标准

1. 同一平台配置至少 3 个有效 Cookie 且有 3～5 个关键词时，最多同时运行 3 个关键词子进程。
2. 理想网络条件下，关键词采集阶段耗时从各关键词耗时之和降低到最慢批次耗时附近；考虑浏览器启动开销，目标至少缩短 40%。
3. 一个 Cookie 凭证失效后立即禁用，不影响使用其他 Cookie 的关键词。
4. 临时风控按指数退避，不产生高频重试。
5. 所有 Cookie 忙碌时等待前序单元释放，并保持 FIFO 公平性。
6. 所有 Cookie 不可用时给出明确安全失败，不无限等待。
7. 单 Cookie 配置继续正常工作，行为退化为串行调度。
8. 不发生跨子进程配置污染、Cookie 并发复用、浏览器进程泄漏或敏感信息泄漏。
9. 前端能够解释每个关键词的实际采集数量，不再把批次累计评论误认为单条内容评论。
10. 爬虫中途失败且已经取得内容或账号时，完整安全部分结果被保留；重试耗尽后报告仍基于这些证据生成。
11. 只有孤立评论或完全空结果时，不得以“部分成功”绕过整个报告的无证据失败保护。

## 16. 后续演进

当后端需要多 Worker 或多机器部署时，将 `GlobalCookieLeaseManager` 的状态和等待协调迁移到 Redis：使用带租期的原子租约、配置版本键、冷却有序集合和发布订阅唤醒机制。当前接口应保持存储实现可替换，使 workflow、调度器和子进程协议无需随分布式迁移重写。

长期可逐步把 MediaSpider 模块级配置改造成实例化运行时，届时可评估从“每关键词独立子进程”迁移到常驻 Worker 或进程池，以降低浏览器冷启动成本；该优化不属于本次范围。
