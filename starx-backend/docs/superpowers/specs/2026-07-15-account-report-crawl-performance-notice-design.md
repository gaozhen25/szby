# 账号报告采集提速与主页链接非阻断提示设计

## 1. 背景与问题定位

账号报告当前会为每个平台依次执行博主主页采集和关键词采集。关键词计划固定生成 3～5 个不重复关键词，并把同一组关键词用于所有支持平台。现有 MediaSpider 默认每个关键词最多采集 30 条内容、单条内容最多采集 10 条评论、详情并发数为 1。

这带来两个用户可见问题：

1. 内容详情和评论读取几乎串行执行。以前端 1.5 秒轮询观察，评论计数虽然能在后端事件产生后及时更新，但必须先等待当前批次的内容详情完成，因此页面长时间看不到评论计数变化。
2. 博主主页链接缺失、格式不匹配、账号不存在或返回空结果时，workflow 把 `creator_url_invalid` 写入平台失败。后续关键词采集实际上仍会继续，但前端先展示红色“平台采集失败”，最终平台也可能被标记为 `partial`，并写入报告的 `sourceMeta.failedPlatforms`。这把可跳过的配置问题错误表达成平台采集故障。

按现有上限计算，每个平台一次报告会采集 3～5 个关键词，每个关键词最多 30 条内容，即理论上 90～150 条内容；若每条读取 20 条评论，则原始采集上限会达到 1,800～3,000 条评论。这个规模不适合账号报告的交互等待时间，也远高于最终报告证据的使用量。

## 2. 目标

1. 将单次 MediaSpider 运行内部的内容详情并发数从 1 调整为 3，缩短内容与评论阶段等待时间。
2. 账号报告专用的关键词内容上限调整为每个关键词最多 10 条；不放大全局配置已经设置的更低上限。
3. 单条内容最多读取 20 条原始评论，继续关闭子评论采集。
4. 博主主页链接无效时，前端明确提示“配置的博主主页链接无效，已跳过主页采集”，随后继续展示关键词采集进度。
5. 主页链接无效不计入平台失败；只要关键词采集成功，平台最终状态为完成，同时保留非阻断提示供用户修正配置。
6. 真正的凭证、网络、风控、运行时或关键词采集异常继续按失败处理，不得被“跳过主页”逻辑吞掉。
7. 不增加 Cookie、完整主页链接、请求头、异常原文等敏感信息的传播路径。

## 3. 非目标

- 不并行执行多个 workflow 或多个 MediaSpider 进程级采集任务。现有运行时会临时修改进程级爬虫配置，跨任务仍由进程锁串行保护。
- 不移除平台请求间隔、重试或风控保护，也不承诺并发数越高速度一定线性提升。
- 不修改关键词生成数量，仍为 3～5 个不重复关键词，每个关键词最多 12 个字符。
- 不修改最终报告证据容量：热门内容最多 20 条、报告评论最多 20 条、单条内容最多使用 3 条评论。
- 不采集子评论，不在前端展示评论正文。
- 不自动猜测、补全或覆盖账号档案中的博主主页链接。
- 不把所有博主采集异常都降级为提示；仅处理可明确识别的主页配置无效场景。

## 4. 方案概览

本次采用“受控内部并发 + 账号报告专用采样上限 + notice/failure 双通道”方案。

```text
账号报告关键词计划（3～5 个关键词）
             │
             ▼
账号报告运行参数收敛
  每关键词内容 ≤ min(全局上限, 10)
  单内容评论 ≤ 20
  内容详情并发 = 3
             │
             ▼
MediaSpider 单任务内部并发采集

博主主页采集
  ├─ 链接无效/账号不存在/空结果
  │      └─ notice：跳过主页，不写平台失败
  └─ 其他真实异常
         └─ failure：记录失败，但仍尝试关键词

关键词采集
  ├─ 成功：平台 completed；已有 notice 继续展示
  └─ 失败：平台 partial/failed，并进入 failedPlatforms
```

该方案保持进程级安全边界不变，只在单次爬虫内部提升受信任的详情任务并发；同时把“配置提醒”和“运行失败”拆成不同领域状态，避免依赖前端根据错误文案猜测语义。

## 5. 采集数量与并发设计

### 5.1 配置项

后端 `Settings` 与 `.env.example` 调整为：

| 配置项 | 默认值 | 作用域 | 说明 |
|---|---:|---|---|
| `MEDIASPIDER_MAX_CONCURRENCY` | 3 | 所有 MediaSpider 单次运行 | 控制同一采集任务内部的详情并发，不并行多个 workflow |
| `MEDIASPIDER_MAX_COMMENTS_COUNT` | 20 | 所有 MediaSpider 单次运行 | 每条内容最多保存 20 条一级评论 |
| `MEDIASPIDER_ENABLE_SUB_COMMENTS` | false | 所有 MediaSpider 单次运行 | 保持不采集子评论 |
| `ACCOUNT_REPORT_MAX_NOTES_PER_KEYWORD` | 10 | 仅账号报告 | 每个平台、每个关键词最多采集 10 条内容 |

`ACCOUNT_REPORT_MAX_NOTES_PER_KEYWORD` 使用正整数校验。账号报告构造每个平台运行参数时执行：

```text
effective_max_notes = min(
    MEDIASPIDER_MAX_NOTES_COUNT,
    ACCOUNT_REPORT_MAX_NOTES_PER_KEYWORD,
)
```

因此运维若把全局内容上限设为 6，账号报告仍只采 6 条，不会被专用默认值反向放大。其他直接使用 `MediaCrawlerService` 的功能继续遵循全局 `MEDIASPIDER_MAX_NOTES_COUNT`，不受账号报告专用上限影响。

### 5.2 账号报告实际规模

调整后，每个平台的关键词原始采集规模为：

- 3 个关键词：最多 30 条内容、600 条一级评论。
- 5 个关键词：最多 50 条内容、1,000 条一级评论。

以上是理论上限，不是保证数量。平台返回不足、去重、过滤、风控或提前结束都会使实际数量更少。博主主页采集产生的内容属于独立采集结果，不纳入“每关键词 10 条”的乘法计算，但仍受其运行参数与平台行为约束。

### 5.3 并发边界

`max_concurrency=3` 只允许同一个爬虫运行中的最多三个详情任务并行。关键词列表的业务顺序、平台之间的 workflow 顺序以及进程级爬虫锁保持现状。

固定请求间隔和平台端响应时间仍会影响总耗时。并发任务必须继续通过现有信号量与运行时配置作用域，异常或取消时释放页面、浏览器上下文和信号量，不新增脱离 workflow 生命周期的后台任务。

配置调整在后端服务重启后生效。实现和验证过程中不得打印 `.env`、Cookie 或完整运行参数。

## 6. 主页链接非阻断提示模型

### 6.1 notice 与 failure 分离

`PlatformState` 新增独立的有序 `notices` 状态，元素继续复用经过公开目录标准化的 `CrawlerFailure` 安全文案结构，但其领域含义为非阻断提示。`failures` 只保存真正影响采集完整性的失败。

平台状态计算规则为：

1. 正在采集时为 `running`。
2. 有成功运行且没有真实失败时为 `completed`，不受 notice 影响。
3. 同时存在成功运行与真实失败时为 `partial`。
4. 只有真实失败且没有成功运行时为 `failed`；仅缺少凭证仍沿用现有 `skipped` 规则。
5. 只有 notice、尚未开始关键词采集时不伪装成成功，保持 `pending` 或当前运行状态；关键词成功后转为 `completed`。

`PlatformCrawlSummary` 在现有失败字段之外增加可选字段：

```text
noticeCode
noticeMessage
noticeSuggestion
```

失败字段与提示字段允许同时存在。例如主页链接无效产生 notice，随后关键词网络超时产生 failure，此时摘要为 `failed`，同时保留两类信息；前端优先强调失败，并以次要样式保留配置提示。

### 6.2 可降级为 notice 的场景

以下场景统一归一化为 `creator_url_invalid` notice：

1. 账号档案没有配置当前平台的博主主页链接。
2. 链接无法解析出与当前平台匹配的公开博主标识。
3. 博主主页采集正常返回，但博主数和内容数均为 0。
4. 博主采集抛出已分类的 `CrawlerExecutionError`，且公开失败代码明确为 `creator_url_invalid`。

上述场景记录固定安全活动：

```text
stage: creator
status: skipped
action: creator_skipped
message: 配置的博主主页链接无效，已跳过主页采集
```

提示建议固定为“请在账号档案中填写该平台真实、完整的博主主页链接”。活动和平台摘要不得包含原始 URL、查询参数或解析出的用户标识。

### 6.3 仍属于真实失败的场景

以下场景继续调用现有 failure 通道：

- 未配置、过期或未生效的平台 Cookie。
- 浏览器启动、平台响应、访问验证、网络超时或运行时兼容问题。
- 博主采集抛出非 `creator_url_invalid` 的已分类异常。
- 关键词采集返回任何已分类或未知异常。

博主采集的真实失败仍不阻断随后关键词尝试，但会使最终平台摘要根据成功情况成为 `partial` 或 `failed`。本次只修正无效主页链接的错误语义，不扩大异常吞并范围。

## 7. workflow 数据流与报告来源

`AccountReportWorkflow` 增加与 `record_failure` 对称的 `record_notice` 边界：

1. `record_notice` 调用 tracker 的 notice 方法，生成 `skipped` 生命周期活动并持久化快照。
2. notice 不增加 `failed_platforms`，也不减少关键词采集机会。
3. 博主阶段完成后，无论是否产生无效链接 notice，只要平台凭证存在，都继续进入关键词循环。
4. `successful_crawls` 仍只由真实成功的采集结果增加。只有 notice 且关键词也未成功，不能误触发报告生成。
5. `failedPlatforms` 仅收录真实 failure。无效主页配置不会污染最终报告的失败平台来源。
6. `unknown_owner_platforms` 继续标记未取得可靠账号归属的平台，证据构建不得把关键词命中的同名作者误认为账号本人。

完成后的公开结果示例：

```json
{
  "platform": "dy",
  "platformName": "抖音",
  "status": "completed",
  "contentCount": 30,
  "commentCount": 120,
  "failureCode": null,
  "noticeCode": "creator_url_invalid",
  "noticeMessage": "配置的博主主页链接无效，已跳过主页采集",
  "noticeSuggestion": "请在账号档案中填写该平台真实、完整的博主主页链接"
}
```

## 8. 前端交互

前端账号报告归一化函数显式读取三个 notice 字段，对旧 workflow 或旧后端缺少这些字段时降级为空值。

进度组件按以下规则展示：

- `failureMessage` 使用现有错误样式和失败建议。
- `noticeMessage` 使用黄色或中性提醒样式，不显示“平台采集失败”标题。
- `creator_skipped` 活动显示“配置的博主主页链接无效，已跳过主页采集”。后续关键词事件到达时，当前活动自然切换为关键词采集，不冻结在提示上。
- 平台状态为 `completed` 且存在 notice 时，显示完成计数，并在计数下保留可操作的配置提醒。
- notice 与 failure 同时存在时，两者分别展示，不用 notice 覆盖真正失败。

前端仍按现有 1.5 秒轮询。评论进度延迟通过后端内容采样和内部并发改善，不额外提高轮询频率，避免无意义地增加 API 压力。

## 9. 安全与兼容性

- notice 文案来自后端固定目录或白名单映射，不直接展示异常原文。
- 主页 URL 仅用于采集和内部哈希判断，不进入 notice、活动、平台摘要或报告失败来源。
- Cookie 继续使用 `SecretStr`，不得进入配置快照、日志、测试输出和 API。
- 新增字段全部可选，旧的 workflow 记录和前端页面保持可读。
- 不修改现有 `failureCode`、`failureMessage`、`failureSuggestion` 契约，其他消费者无需同步迁移。
- 报告证据继续执行内容、评论和账号标识的既有限制与去身份化逻辑。

## 10. 测试策略

### 10.1 后端配置与运行参数

1. `Settings` 默认详情并发为 3、单内容评论上限为 20、账号报告每关键词内容上限为 10。
2. `.env.example` 与代码默认值一致，子评论仍为关闭。
3. 账号报告传给 crawler 的 `max_notes_count` 为 `min(全局上限, 10)`。
4. 全局上限小于 10 时保持更低值；其他 MediaSpider 调用仍使用全局值。
5. 每个平台和每个关键词分别应用上限，不把 10 误解释成整份报告总量。

### 10.2 tracker 与 workflow

1. `creator_url_invalid` notice 生成 `skipped` 活动和三个 notice 摘要字段，不写入 `failures`。
2. notice 后关键词成功，平台状态为 `completed`，notice 仍存在。
3. notice 后关键词失败，真实 failure 决定平台状态和失败摘要。
4. 缺失链接、平台不匹配链接、空博主结果和已分类无效链接异常都继续执行关键词采集。
5. 非无效链接的博主异常继续记录真实 failure，并仍尝试关键词。
6. 无效链接不进入 `sourceMeta.failedPlatforms`；真实关键词失败继续进入。
7. 只有 notice 且没有任何成功采集时，workflow 仍按“无成功采集”规则失败，不生成空报告。
8. 所有活动和快照均不包含 URL、Cookie、请求头、用户标识或异常原文。

### 10.3 前端

1. 归一化函数正确解析 notice 字段，并兼容缺失字段的旧记录。
2. 平台完成且有 notice 时同时展示完成计数与非红色配置提醒。
3. `creator_skipped` 后出现关键词活动时，当前状态更新为关键词采集。
4. notice 不渲染“平台采集失败”；真正 failure 仍使用失败样式。
5. notice 与 failure 同时存在时均可见，且失败优先级更高。

### 10.4 回归验证

后端测试统一使用 `conda run -n starx pytest ...`。依次运行配置、账号报告 workflow/进度、MediaSpider 定向测试与后端全量测试；前端运行账号报告组件和归一化测试，再运行前端全量测试。必要的真实配置探测只输出公开状态与计数，不输出任何凭证。

## 11. 验收标准

1. 重启后单次 MediaSpider 内容详情并发上限为 3，多个 workflow 仍不会并发污染进程级配置。
2. 账号报告每个平台生成 3～5 个关键词，每个关键词最多采集 10 条内容。
3. 每条内容最多读取 20 条一级评论，子评论保持关闭。
4. 配置无效或不存在的博主主页时，前端显示“配置的博主主页链接无效，已跳过主页采集”，并继续展示关键词采集。
5. 关键词成功后平台显示完成，无效主页提示不进入 `failedPlatforms`。
6. 真正的关键词或平台运行异常仍显示“平台采集失败”及安全建议。
7. 最终报告仍最多使用 20 条内容证据和 20 条评论证据，其中单条内容最多 3 条评论。
8. 新增定向测试、后端全量测试和前端全量测试通过，输出中不存在 Cookie 或其他敏感信息。
