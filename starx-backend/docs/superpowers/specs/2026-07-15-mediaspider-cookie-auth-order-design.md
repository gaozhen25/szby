# MediaSpider Cookie 认证顺序修复设计

## 1. 背景

账号报告使用后端内嵌的 MediaSpider 运行时。当前小红书、抖音和快手都会在新建浏览器上下文后，先从该上下文创建客户端并执行登录态探测。后端默认不保存登录状态，因此新上下文最初没有配置 Cookie，首次探测失败是预期的待登录状态。

提交 `f8d1cda` 在首次探测失败后、Cookie 登录执行前加入了认证失败守卫。结果是配置 Cookie 尚未注入浏览器就被判定为失效，三个平台的 `login_by_cookies()` 都不可达。前端展示的 `credentials_expired` 因而是后端顺序回归产生的误判，不是平台对 Cookie 的真实验证结果。

本设计覆盖并修正旧设计中“首次登录态探测失败即可判定 Cookie 失效”的行为。

## 2. 目标

1. 小红书、抖音、快手在首次登录态探测失败后，必须先执行所配置的登录方式并刷新客户端 Cookie。
2. Cookie 登录只有在注入完成后的二次探测仍失败时，才转换为 `credentials_expired`。
3. 已有浏览器登录态首次探测成功时，不重复登录，也不修改 Cookie。
4. 二维码和手机号登录保持原有流程，不因 Cookie 专用校验改变交互行为。
5. Cookie、请求头和底层异常原文继续禁止进入日志、异常公开文本、进度快照和测试输出。
6. 三个平台共享同一认证编排，避免后续只修复单个平台造成行为漂移。

## 3. 非目标

- 不通过开启 CDP、切换有头浏览器或复用浏览器 Profile 掩盖认证顺序问题。
- 不改变 Cookie 的配置来源、平台字段映射和 `Settings` 生命周期。
- 不修改账号报告 API、前端错误展示或数据库结构。
- 不在本次修复中实现验证码自动处理或新的平台风控识别。
- 不保证任何过期 Cookie 能登录成功；本次保证的是 Cookie 会被真实应用并验证。

## 4. 方案比较

### 4.1 采用：共享认证编排函数

在 `app/services/mediaspider/runtime/auth.py` 中提供一个异步认证编排函数。调用方传入平台代码、登录类型以及三个无参异步动作：登录态探测、执行登录、刷新客户端 Cookie。

编排顺序为：

```text
首次探测
  ├─ 成功：直接返回
  └─ 失败：执行登录 → 刷新客户端 Cookie
                  ├─ 非 Cookie 登录：保持原流程并返回
                  └─ Cookie 登录：二次探测
                                  ├─ 成功：返回
                                  └─ 失败：抛 CrawlerAuthenticationError
```

优点是认证状态机只有一份，三个 `core.py` 只负责构造平台 Login 对象并提供平台特有的探测参数。该函数不接触 Cookie 字符串和浏览器对象，安全边界清晰，也可以用纯异步桩进行无网络测试。

### 4.2 未采用：三个平台分别移动守卫

直接在每个 `core.py` 中复制“登录、刷新、二次探测、抛错”逻辑，单文件改动较小，但会形成三份相同状态机。未来调整认证策略时容易遗漏某个平台。

### 4.3 未采用：仅对齐独立脚本的 CDP 配置

把后端改成有头 CDP 并保存 Profile 可以复用已有登录态，但不能证明后端配置 Cookie 已应用，还会引入端口、Profile 并发和部署环境依赖。因此它只能作为运行模式选择，不能替代认证顺序修复。

## 5. 模块与接口设计

### 5.1 认证编排

`runtime/auth.py` 负责：

- 定义异步动作的类型边界。
- 按固定顺序调用探测、登录和刷新。
- 仅在 Cookie 注入后的二次探测返回 `False` 时调用现有认证失败守卫。
- 不捕获探测、登录或刷新抛出的异常，让运行时分类器按真实异常类型处理。

概念接口为
`ensure_authenticated(platform, login_type, probe, login, refresh) -> None`，
其中 `probe` 返回布尔值，`login` 与 `refresh` 不返回业务数据。

该函数不接受或返回 Cookie 字符串，避免新增敏感信息传播路径。

### 5.2 平台接入

小红书、抖音、快手的 `start()` 保持浏览器启动、页面访问和客户端创建逻辑不变。创建客户端后：

1. 定义延迟登录动作；只有首次探测失败并调用该动作时，才构造平台 Login 对象并执行 `begin()`。
2. 将平台 `pong`、延迟登录动作和 `client.update_cookies` 适配为无参异步动作。
3. 交给共享编排函数。
4. 认证完成后继续现有 search、creator 或 detail 流程。

平台差异仅留在适配层：

- 小红书、快手的探测为无参 `pong()`。
- 抖音探测需要传入当前 `browser_context`。
- 三个平台刷新 Cookie 时继续使用各自的 `cookie_urls`。

## 6. 错误处理

- 首次探测 `False` 只表示当前浏览器上下文尚未登录，不能生成公开失败。
- Cookie 登录后二次探测 `False` 才产生 `CrawlerAuthenticationError`，随后仍由现有分类器转换为 `credentials_expired`。
- 探测动作若抛异常，共享编排不得吞掉或改写为认证失败；异常继续进入现有 `classify_crawler_error()`。
- 登录或刷新 Cookie 失败同样保留真实异常类型，并由安全分类边界清除敏感详情。
- 本次不改变平台客户端内部 `pong()` 对返回数据的判断规则；其网络异常粒度可在后续独立设计中进一步收紧。

## 7. 测试设计

采用测试驱动开发，先替换当前固化回归的测试并确认失败，再修改生产代码。

### 7.1 共享编排单元测试

覆盖以下顺序和分支：

1. 首次探测成功：调用序列只有 `probe`。
2. 首次失败、Cookie 注入后二次成功：序列严格为 `probe → login → refresh → probe`，不抛异常。
3. 两次探测均失败：完成登录和刷新后抛 `CrawlerAuthenticationError`。
4. 二维码或手机号登录：首次失败后执行登录和刷新，不触发 Cookie 专用二次失败守卫。
5. 探测、登录、刷新任一步抛出的异常保持原类型，不被改写为凭证失效。

### 7.2 三平台集成级单元测试

使用现有 fake Playwright 上下文，不发起网络请求。每个平台都验证：

- 初始 `pong=False` 时 Login 对象会被构造并执行。
- `update_cookies` 在第二次 `pong` 前执行。
- 第二次 `pong=True` 时平台启动继续到采集分支。
- 第二次 `pong=False` 时才得到 `CrawlerAuthenticationError`。

测试不得包含真实 Cookie，只使用固定哨兵值，并继续断言序列化与异常文本不泄漏哨兵。

### 7.3 回归验证

使用 `starx` conda 环境执行：

1. 认证编排与错误分类定向测试。
2. MediaSpider service、runtime、平台 runtime、配置及安全日志相关测试。
3. 账号报告 workflow、进度和 API 测试。
4. 后端完整 `pytest`，确认没有跨模块回归。

若本机网络和平台状态允许，再用当前小红书配置执行一次限制数量、关闭评论的真实探测；真实探测只输出事件、计数和公开失败代码，不输出 Cookie 或请求头。自动化测试仍是合并门槛，平台实时结果不作为唯一判据。

## 8. 完成标准

1. 三个平台都由共享认证编排控制顺序。
2. 自动化测试证明 Cookie 登录会在首次失败后真实执行，并在刷新后再次验证。
3. `credentials_expired` 不再由空上下文的首次探测直接产生。
4. 现有敏感信息安全测试继续通过。
5. MediaSpider、账号报告相关测试和后端完整测试均通过。
